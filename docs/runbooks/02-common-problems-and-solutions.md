# Landing Zone 常见问题与标准解决方案

## 1. 多账号到底按什么拆

### 问题

很多团队不知道按业务、环境、团队还是成本中心拆账号。

### 建议

优先级：

1. 安全边界
2. 环境边界
3. 团队/业务边界
4. 成本边界

生产、测试、开发、沙箱尽量分开。安全、日志、网络、共享服务建议独立。

## 2. 管理组/OU 是否要完全照组织架构

不建议。

组织架构经常变，云资源层级应该围绕策略、合规和隔离来设计。组织架构可以通过标签、成本中心、owner 字段表达。

## 3. 为什么不把所有权限放到一个超级管理员

因为超级管理员方便但不可控：

- 容易误操作。
- 难审计。
- 离职交接风险大。
- 不符合最小权限。

标准解法：角色拆分 + JIT/PIM + break-glass。

## 4. 多云是不是一定要完全统一

不应该强行 1:1 统一。

正确方式是：

- 统一治理模型。
- 保留云厂商原生差异。
- 用 adapter 做映射。

例如 AWS Account、Azure Subscription、GCP Project 都可以抽象成 ResourceContainer，但底层生命周期、权限和限制不同。

## 5. Landing Zone 和 Kubernetes 平台是什么关系

Landing Zone 是云基础地基，Kubernetes 平台是运行时平台。

顺序通常是：

```text
Landing Zone -> Network/Security/Identity -> Kubernetes Cluster -> App Platform -> Workloads
```

如果没有 Landing Zone，K8s 集群会缺少统一网络、日志、安全、成本和账号边界。

## 6. 如何低成本做个人项目

不要一开始真实创建大量云资源。

推荐：

- 使用 YAML 蓝图建模。
- 生成 IaC 模板但默认不 apply。
- 用 mock blueprint 演示企业结构。
- 用 policy 检查体现治理能力。
- 用报告输出体现架构能力。

## 7. 如何产生收益

可能路径：

1. 开源项目积累 Star，作为求职背书。
2. 写文章/视频/课程，讲多云 Landing Zone 设计。
3. 提供中小企业云账号治理咨询。
4. 做 SaaS 化版本：上传 blueprint，生成报告和风险评分。
5. 做企业内部平台插件：账号申请、权限申请、策略检查。

最现实的第一收益不是直接卖软件，而是提升求职和接私活可信度。

## 8. 项目过大怎么办

用 MVP 切：

- 第一阶段只做 AWS。
- 第二阶段加 Azure/GCP 模型。
- 第三阶段加 IaC 生成。
- 第四阶段加策略。
- 第五阶段加 UI。

不要一开始做完整企业平台。

## 9. Terraform state 容易互相影响

按云、阶段（`00-bootstrap` … `70-workload-onboarding`）、环境拆分 state；后端启用加密和锁；生产 apply 单独审批；禁止本地 state 进入仓库。

## 10. 公司已有存量账号怎么纳管

先盘点账号、权限、网络、日志、账单，再设计目标结构。新业务走新 Landing Zone，存量业务分阶段纳管，不建议一刀切迁移。

## 11. 安全规则影响业务上线怎么办

Guardrails 分级：阻断 / 告警 / 建议。对 Sandbox 宽松，对 Prod 严格。提供例外申请流程，并带 reason、owner、expiry_date 和补偿控制（参见 [03-security-governance-design](../design/03-security-governance-design.md) 的例外机制）。

## 12. 成本标签没人填怎么办

Terraform module 强制标签输入；Policy 阻止缺标签资源；默认标签在 provider/module 层合并；成本报表按标签输出。

## 13. 多团队不知道怎么接入

提供 workload onboarding 模板、账号申请表、权限申请表、网络接入清单和上线前检查表。

## 14. 云厂商服务名不同，文档难维护

统一使用共同能力域：org、identity、network、security、logging、finops；在每朵云目录下写原生实现；用 [references.md](../references.md) 维护官方文档链接。

## 15. 什么时候可以让业务团队自助创建账号/订阅/项目

不要一开始就完全自助。先把申请信息、审批人、成本中心、网络域、数据分级和默认策略固定下来，再逐步开放 vending。

推荐阶段：

1. 平台团队手工审核 PR。
2. 标准表单生成 PR。
3. 自动 plan + 人工 approve。
4. 低风险 sandbox 自动 apply，prod 仍需审批。

## 16. 存量资源要 import 还是重建

优先级：

1. 关键生产资源：import 到 Terraform，避免重建。
2. 可替换的非生产资源：可以重建，但必须通知 owner。
3. 高风险资源（网络、IAM、日志、KMS）：先文档化现状，再小步 import。

Import 后第一件事不是 apply，而是跑 plan，确认 Terraform 不会立刻替换资源。

## 17. Break-glass 怎么设计才不变成后门

Break-glass 是应急流程，不是常驻管理员。

最低要求：

- 独立账号或角色，强 MFA。
- 凭证保管和启用流程分离。
- 每次使用自动告警。
- 使用后补工单、补 PR、补复盘。
- 定期演练登录和撤销，但不用于日常变更。

## 18. 如何处理策略例外

例外必须像资源一样有生命周期。

每个例外至少包含：

- `owner`
- `reason`
- `scope`
- `expiry_date`
- `risk_level`
- `compensating_control`

到期后默认关闭；延期必须重新审批。不要把例外直接写成永久 allow。

## 19. 多云 Landing Zone 要不要统一网络

不要默认做跨云全互联。跨云网络是高成本、高复杂度、高故障域的设计。

推荐原则：

- 管理面统一，数据面按业务需求互联。
- 先打通身份、日志、成本、策略，再考虑网络。
- 跨云链路只服务明确 workload，不做“全网互通”。
- 生产跨云互联必须有路由域、DNS、流量检查和回滚方案。

## 20. 为什么 plan 通过了 apply 仍可能失败

常见原因：

- 云 API 最终一致性或权限传播延迟。
- 配额、实名、计费、区域开通等控制台前置条件未满足。
- 组织策略在 apply 时阻断资源创建。
- provider schema 支持但目标云服务当前地域不支持。

解决方式：把 plan 前置检查、配额检查、区域支持和最小 sandbox apply 纳入发布门禁。

## 21. 如何做日志留存和删除

日志不是“能查到就行”，而要满足防篡改、保留期和可取证。

建议：

- 操作审计日志集中到专用日志账号/项目/订阅。
- 生产日志启用版本化、保留期、对象锁或等价能力。
- 日志读取和日志删除权限分离。
- 删除日志必须经过合规审批，并保留删除审计。

## 22. 如何判断一个模块能进入生产

模块生产就绪至少满足：

- README、输入、输出、示例和安全注意事项齐全。
- 默认不创建高成本或高风险资源。
- 默认安全，危险开关显式 opt-in。
- fmt、validate、lint、security scan、policy 测试通过。
- 有回滚路径和 state 兼容说明。
- 已在 sandbox 做最小 apply 或明确标注只支持静态验证。

## 23. Landing Zone 和平台团队职责怎么划分

平台团队拥有 landing zone 的共享能力和护栏；业务团队拥有应用资源。

平台团队负责：账号/订阅/项目售卖、身份边界、网络底座、日志、安全策略、成本标签、CI 门禁。

业务团队负责：应用架构、资源申请、数据分类、成本 owner、运行时告警、业务连续性。

边界不清会导致两种坏结果：平台团队替业务背锅，或业务团队绕过平台治理。

## 24. 什么时候需要 ADR

以下变更必须新增或更新 ADR：

- 改变云原生模型选择，例如从 Hub-Spoke 改成全网格。
- 改变 state 拆分或后端策略。
- 改变生产默认安全策略。
- 引入跨云共享抽象或工具层。
- 会导致已有资源 state 地址迁移或强制替换的模块设计变更。
